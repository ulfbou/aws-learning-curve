# ADR-011: Bounded Learning Artifact Transactions

- Status: Accepted
- Date: 2026-11-02

## Context

AWS Learning Curve is a learner-centered system for building, practising, and retaining usable AWS mental models.

AI can contribute useful semantic work, including explanations, comparisons, questions, scenarios, and misconception remediation. However, free-form AI output must not directly control repository paths, system fields, or repository mutation.

Passing the complete repository into every interaction would also introduce irrelevant context, make responses harder to review, and encourage large rewrites.

The repository therefore needs a bounded hand-off between deterministic tooling and AI collaboration.

## Decision

AI-assisted repository changes will use bounded learning-artifact transactions:

```text
learning need
    ->
bounded repository context
    ->
AI candidate transaction
    ->
deterministic validation
    ->
dry-run preview
    ->
human review
    ->
repository application
```

The transaction boundary separates semantic proposal from deterministic repository mutation.

## Responsibilities

### Python owns

Python is authoritative for:

- repository loading;
- object lookup;
- repository paths;
- normalization;
- schema validation;
- repository validation;
- source-reference validation;
- revision checks;
- expected-content-hash checks;
- timestamps;
- content hashes;
- generation-run identifiers;
- dry-run behavior;
- repository mutation;
- operation results.

### AI owns

AI performs semantic learning work within the supplied context.

AI may propose:

- creating a learning object;
- updating a learning object;
- leaving an object unchanged;
- improving an explanation;
- adding examples or non-examples;
- creating a contrast;
- generating practice;
- surfacing a possible misconception;
- identifying an unresolved semantic question.

AI results are candidates only.

AI must not:

- select repository paths;
- assign system-managed fields;
- mutate files directly;
- publish candidate material;
- alter read-only source material;
- claim learner mastery;
- claim that a misconception has been corrected without learner interaction.

### Learner owns

The learner:

- states the learning need;
- reviews proposed semantic changes;
- decides whether the proposal is useful;
- approves application;
- uses the resulting artifact;
- records what remains unclear.

## Bounded context

The AI receives only the repository material required for the current learning need.

Bounded context exists to:

- improve relevance;
- reduce irrelevant repository exposure;
- preserve the current task boundary;
- support smaller, reviewable changes;
- prevent broad speculative rewrites.

Bounded context does not authorize AI decisions. It defines the material available for semantic work.

## Transaction operations

The initial transaction model supports:

```text
create
update
unchanged
```

An update must identify the intended repository object and include concurrency information supplied by deterministic tooling, such as:

```text
target semantic ID
expected revision
expected content hash
```

Python resolves the semantic ID to a repository-owned path.

The AI never chooses that path.

## Existing object kinds

The system must reuse existing learning-object kinds before introducing new ones:

```text
concept
misconception
question
scenario
procedure
competency
learning_unit
```

A new kind requires a demonstrated modeling gap arising from repeated real use.

Presentation formats alone do not require new persistent kinds.

For example:

- a comparison may remain a contrast concept;
- a practice set may remain a selection of existing questions and scenarios;
- a study guide may remain a generated view;
- a concept map may remain a visualization of existing relationships.

## Source material

Registered source material may be included in bounded context when relevant.

Source fragments:

- provide learning context;
- help distinguish source material from later synthesis;
- support safe representation of existing material;
- may be cited by candidate semantic changes.

Read-only source material must not be modified or included as a modified file in a resulting transaction.

## Repository content state

Statuses such as:

```text
candidate
published
deprecated
rejected
```

describe repository objects.

They do not describe learner understanding.

In particular:

- a published object does not imply mastery;
- a candidate explanation may still be useful during study;
- accepting a repository change does not prove that learning occurred.

## Review and application

Application remains human-reviewed.

A transaction may be:

- prepared;
- validated;
- previewed as a dry-run;
- rejected;
- revised;
- applied after review.

Successful validation means that the proposed repository mutation satisfies the deterministic contract. It does not mean that the learning artifact was pedagogically effective.

## Consequences

### Positive

- Semantic work and repository mutation have distinct responsibilities.
- AI changes remain small and reviewable.
- Existing repository validation can be reused.
- Concurrent changes can be detected before mutation.
- Source references remain available without becoming the product purpose.
- The model supports iterative learning work without autonomous publication.

### Costs

- Every applied AI proposal requires a structured transaction.
- Human review remains part of the workflow.
- Context construction requires deterministic repository tooling.
- The first implementation supports fewer retrieval and mutation capabilities than a free-form agent.

These costs are accepted because they preserve clarity, safety, and incremental development.

## Non-goals

This decision does not introduce:

- a new artifact taxonomy;
- embeddings;
- semantic search;
- graph infrastructure;
- automatic mastery inference;
- automatic publication;
- autonomous study planning;
- Git branch, commit, push, or merge behavior;
- a multi-user platform.

## Implementation status

This ADR establishes the architectural boundary.

The bounded learning-context workflow is implemented by
`scripts/content_workflow.py` and
`scripts/learning_workflow/engine.py`.

The implementation must preserve the repository ownership boundary:

- `master` owns frontend code, schemas, tooling, tests, and CI/CD policy.
- `backend` owns canonical `content/**`.
- The tooling root is derived from the frontend checkout.
- The content workspace is supplied explicitly.
- Dry-run and execution consume the same prepared plan.

Deterministic repository validation does not claim to prove learner mastery or
pedagogical effectiveness.
