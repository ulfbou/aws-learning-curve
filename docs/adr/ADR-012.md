# ADR-012: Learning Context Workflow

- Status: Accepted
- Date: 2026-11-02

## Context

ADR-011 establishes that AI proposes candidate learning-artifact transactions while deterministic Python tooling owns repository operations.

The next runtime increment must prove that boundary through one real learning interaction without expanding the repository into a general AI tutor, adaptive-learning platform, semantic-search system, or knowledge-graph project.

The first implementation therefore needs one complete vertical loop rather than a broad query framework.

## Decision

The next runtime increment will implement one bounded learning-context workflow:

```text
learning need
    ->
learning query
    ->
bounded learning context
    ->
AI candidate transaction
    ->
Python dry-run
    ->
human-reviewed apply
    ->
structured operation result
    ->
short study use
    ->
explicit unresolved point
```

The initial study scenario is:

```text
Understand the difference between IAM users, roles, and policies.
```

## Learning need

A learning need is a learner-stated goal, uncertainty, or misconception.

Examples:

```text
Understand the difference between IAM users, roles, and policies.

I understand IAM roles in theory, but I confuse trust policies
with permission policies.

Create practice that helps me decide when a workload should use
a role instead of long-lived credentials.
```

A learning need is not a repository mutation request by itself.

It guides deterministic context retrieval and the subsequent AI interaction.

## Learning query

A learning query is a deterministic request over repository state.

The first implementation is limited to:

- exact semantic ID;
- alias;
- keyword;
- tag;
- object kind;
- content status;
- direct relationships.

The query may select relevant:

- concepts;
- misconceptions;
- questions;
- scenarios;
- procedures;
- competencies;
- learning units;
- registered source fragments.

The initial implementation must not depend on:

- embeddings;
- semantic similarity;
- inferred mastery;
- adaptive ranking;
- deep graph traversal;
- automatically generated learning paths.

## Learning context

A learning context is the bounded machine-readable result of a learning query.

It should contain only the material required for the current interaction.

The smallest useful contract should be implemented first. It may include:

```yaml
schema_version: "1.0"
learning_goal: Understand the difference between IAM users, roles, and policies.
query:
  ids: []
  aliases: []
  keywords:
    - IAM
    - user
    - role
    - policy
  tags:
    - iam
  kinds:
    - concept
    - misconception
    - question
    - scenario
  statuses:
    - candidate
    - published
  include_direct_relationships: true
matches: []
related_objects: []
available_source_material: []
context_limits:
  direct_relationships_only: true
  maximum_objects: 20
```

This structure is illustrative. The implementation must introduce only the fields required by the first complete loop.

The learning context exists to improve relevance. It does not authorize AI actions.

## Candidate transaction

The AI receives the bounded context and returns one machine-readable candidate transaction.

The transaction may propose:

```text
create
update
unchanged
```

The AI supplies semantic content.

Python enriches or validates repository-controlled information, including:

- target path;
- current revision;
- expected content hash;
- timestamps;
- new revision;
- new content hash;
- generation-run data;
- source-reference consistency.

The AI response must not contain an authoritative repository path or authoritative system-field values.

## Dry-run

The dry-run performs the same deterministic validation used for application, except that it does not mutate the target repository.

It reports:

- intended creates;
- intended updates;
- unchanged objects;
- validation failures;
- revision or hash conflicts;
- source-reference failures;
- warnings;
- the exact repository effect that would be attempted.

A successful dry-run does not imply that the learner has learned anything. It means only that the proposed repository operation is valid against the current repository state.

## Human review

The learner reviews:

- the semantic proposal;
- the represented source context;
- the proposed repository change;
- the dry-run result.

Application requires explicit human review.

The workflow does not automatically promote, publish, commit, push, merge, or deploy the result.

## Apply

Prepare creates one immutable, hash-protected plan containing a
Python-owned operation timestamp and the exact proposed output.

Dry-run and execution consume that same prepared plan against the same explicit
content workspace. Execution rejects a plan if its expected repository state is
stale or if the plan has been modified.

Python owns:

- repository path resolution;
- conflict detection;
- schema validation;
- repository validation;
- file writing;
- best-effort rollback if a multi-file operation fails;
- production of the structured operation result.

A multi-file write must not be described as atomic unless the implementation provides actual atomicity.

## Operation result

The workflow returns a structured operation result.

The term `operation result` is used instead of `learning outcome` because repository tooling cannot determine whether learning occurred.

Example success result:

```yaml
schema_version: "1.0"
operation: apply
result: success
learning_goal: Understand the difference between IAM users, roles, and policies.
changes:
  created: []
  updated:
    - aws.iam.role
  unchanged: []
warnings: []
next_actions:
  - review the updated comparison
  - use the artifact in a short study session
  - record what remains unclear
```

Example conflict result:

```yaml
schema_version: "1.0"
operation: apply
result: failure
learning_goal: Understand the difference between IAM users, roles, and policies.
failure:
  category: changed_context
  object_id: aws.iam.role
  reason: The object changed after the learning context was created.
next_actions:
  - create a fresh bounded learning context
```

The initial implementation should prefer one small versioned result contract over several speculative schemas.

Separate contracts should be introduced only when distinct validation needs or lifecycles are demonstrated.

## Study use and unresolved point

The runtime workflow is not complete merely because a repository update succeeds.

The resulting learning artifact must be used in one short study interaction.

After use, the learner records an explicit unresolved point, for example:

```text
I now understand role assumption, but trust policies are still unclear.
```

The first implementation does not require a full private learner-state subsystem.

The unresolved point may initially remain a user-provided input to the next bounded interaction.

## Command boundary

The workflow should keep repository mutation separate from Git administration.

The intended command responsibilities are:

```text
query
prepare
apply
```

Git responsibilities remain outside the learning workflow:

```text
branch
commit
push
pull request
merge
deployment
```

The implementation should reuse existing deterministic repository primitives rather than duplicate:

- object loading;
- normalization;
- path derivation;
- hashing;
- schema validation;
- repository validation;
- source-reference checks;
- transaction enrichment.

## Exit criteria for the runtime increment

The following complete loop must work for one real IAM study need:

```text
learning need
    ->
bounded deterministic context
    ->
one AI candidate transaction
    ->
dry-run
    ->
human-reviewed apply
    ->
structured operation result
    ->
short study use
    ->
explicit unresolved point
```

The deterministic acceptance test uses isolated IAM user, IAM role,
IAM policy, and user-versus-role-versus-policy fixtures. It proves bounded
direct-relationship retrieval, preparation, dry-run without mutation,
execution of the same prepared result, repository validation, and stale-plan
rejection.

An actual learner interaction remains a human acceptance activity and is not
inferred from repository-tooling success.

## Explicitly out of scope

The first implementation does not include:

- embeddings;
- semantic similarity search;
- deep relationship traversal;
- graph infrastructure;
- automatic recommendations;
- learner adaptation;
- automatic mastery judgments;
- automatic study planning;
- new artifact kinds;
- automatic Git operations;
- automatic publication;
- generalized study-session orchestration;
- multi-user support.

## Consequences

### Positive

- The next runtime change has a narrow acceptance boundary.
- Repository context remains relevant and reviewable.
- Existing object kinds receive real-use testing.
- The system produces an actionable result without claiming learning success.
- The learner's unresolved point can drive the next interaction.

### Costs

- Retrieval is intentionally limited.
- The first scenario is not a general tutor implementation.
- Learner feedback is initially explicit and minimally represented.
- Additional abstractions must wait for evidence from use.

These constraints are intentional.
